# Korean Moshi fine-tuning notes

Upstream was checked against `kyutai-labs/moshi` and `kyutai-labs/moshi-finetune`
main on 2026-09-17. Recheck before a long training run because these are live APIs.

## Dataset contract

`moshi-finetune` loads JSONL rows shaped as `{"path": ..., "duration": ...}`
through `sphn.dataset_jsonl`. Audio must be stereo: channel 0/left is the audio
generated by Moshi (assistant), and channel 1/right is user input. A JSON file
with the same basename must contain:

```json
{"alignments": [["word", [0.1, 0.3], "SPEAKER_MAIN"]]}
```

The interleaver treats `SPEAKER_MAIN` as Moshi's text stream. DuplexForge writes
assistant words with that label and user words as `SPEAKER_USER`. Current TTS
backends do not expose forced alignment, so word boundaries are deterministic
approximations distributed across each utterance. Replace them with backend
alignments or forced alignment before a high-quality production run.

## Architecture and adaptation plan

- Mimi is a causal 24 kHz neural codec, configured at 12.5 frames/s in the
  current PyTorch loader. `moshi-finetune` explicitly sets it to eval mode and
  freezes every parameter. Keep it frozen initially.
- The temporal/main Transformer models progression through time. Upstream LoRA
  replaces linear layers throughout the Moshi LM; it is not currently exposed
  as a temporal-only target list in the training YAML.
- The depth/Depformer predicts audio codebooks within a timestep. Because the
  upstream replacement is broad, a strict “temporal LoRA, depth frozen” study
  requires an upstream code change and is not silently implemented here.
- `text_emb`, text output projection, audio embeddings, and Depformer embeddings
  are separate model components. `lora.ft_embed` optionally full-finetunes
  embeddings while linear layers use LoRA.
- The first Mimi codebook is treated as semantic and the official recipe gives
  it extra loss weight (`first_codebook_weight_multiplier: 100`).
- The checked model uses SentencePiece. Korean coverage, unknown behavior, and
average tokens/sentence depend on the exact tokenizer checkpoint. Run the
`scripts/audit_tokenizer.py TOKENIZER.model KOREAN_SENTENCES.txt` audit against
the downloaded checkpoint before setting `ft_embed: true`;
  do not extend or replace the tokenizer automatically because that also changes
embedding/output dimensions.

An audit of the checked Moshiko tokenizer on eight representative Korean
sentences produced 498 tokens (62.25 tokens/sentence), zero unknown tokens, and
zero directly represented Hangul syllables. The zero unknown rate comes from
fallback decomposition rather than good Korean coverage. This is inefficient
enough that a Korean tokenizer/embedding adaptation experiment is required;
LoRA on the English text stream alone should not be treated as the final plan.

## Conservative first experiment

Use `configs/korean_moshi_finetune.yaml`. It retains upstream rank 128, scaling
2, learning rate 2e-6, 100-second chunks, semantic-codebook multiplier 100, and
checkpoint/evaluation frequency 100. Batch size is reduced from the upstream
H100-oriented example (16) to 1 for a safer first integration run, with four
microbatches accumulated per optimizer step through upstream's
`num_microbatches`; increase it only after measuring memory. Upstream exposes
steps rather than epochs in its current config.

Before scaling, generate 10–20 samples, validate them, and run a single batch
through the real `build_data_loader`. That final GPU/Mimi integration requires a
local `moshi-finetune` installation and model checkpoint and is intentionally not
mocked as proof of compatibility.
